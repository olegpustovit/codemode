# Microapps ID rollout preparation

This is codemode's local preparation for the Microapps ID proposal T37+. Work is isolated on `identity-oidc` in the sibling `codemode-identity` worktree; the original `main` checkout stays unchanged. Production is not deployed by this work. Read-only health confirms the existing build `d45e6106a3a6`, schema 20.

## ID-01: private existing-account linking

Forward migration `0021_identity_subjects.sql` creates a separate global authentication mapping: one subject per local user, one user per subject, a cascading user FK and a 1–255 byte subject constraint. No existing table/column is rewritten. Tenant-scoped `codemode_tenant` connections receive no mapping privileges. Subjects never enter public `User` JSON.

`Sessions::link_identity` accepts only SDK-verified subject/email claims, validates their shape, resolves a bound subject before exact normalized email, and links an existing account in one transaction. Concurrent first links converge on the canonical subject binding. A second subject cannot take an already bound local account. Unknown identities do not create users or tenants through this primitive, even on an empty database. A changed verified email cannot move a bound subject. Existing legacy addresses can link independently of the current signup allowlist, while ordinary password registration retains its original allowed-address policy.

Local IDs, tenant IDs, administrator flags, password hashes and timestamps stay unchanged. So do tenant-owned source IDs, encrypted upstream credentials, workspaces, policies, scripts, agent tokens, stored OAuth grants and execution/tool-call history. Neither a global ID role nor a claim creates local authority or adopts the legacy nil tenant. Existing browser/password and agent authentication remain available.

Native PostgreSQL cases cover twelve concurrent first links, same-subject/different-email and competing-subject races, private JSON/RLS boundaries, precise seeded data snapshots, legacy password/token access, unknown/invalid claims, no empty-instance bootstrap, injected insertion failure with rollback/retry, both uniqueness constraints, FK/byte constraints and cascade cleanup. The shared schema-head assertion moves from 20 to 21; the existing newer-migration/known-checksum rollback case still passes. SQLx prepare/check uses owned PostgreSQL 18, generates four query descriptors and prunes eleven obsolete execution/approval descriptors. Runtime queries stay compile-time checked; no dependency or toolchain change is introduced.

Qualification: the workspace fast tier passes 114 cases under the unchanged 2-second unit/5-second integration deadlines (slowest 2.708 s). The final focused identity-related tier passes four cases in 3.66 s including a 3.12 s build (slowest 0.535 s). Formatting, Clippy, SQLx metadata freshness and cargo-deny advisory/license/ban/source checks pass; repository-style test unwrap/shared-fixture warnings remain. The measured gateway rebuild after touching the new core module is 1.93 s, within the 10 s core-edit budget; this narrow result does not erase historical build-budget misses elsewhere. Unchanged embedded UI `e16dc707d79d` is reused from the existing staged artifact. Worker/provider acceptance, exhaustive tier and native browser flows are not newly qualified by this foundation.

Default-off SDK login/callback/logout wiring is now implemented in ID-05 below. Remaining: SDK publication/pin; incumbent UI; actual-provider/tenant/workspace/agent qualification; persistent eval deployment smokes and rollback guards; production registration and the per-app human gate. Upstream provider consent and existing external acceptance gates remain unperformed. Production fixtures, passwords and source connections are untouched.


## ID-02: private Microapps ID session storage

Forward migration 22 adds `identity_sessions` separately from legacy password sessions, with purpose-prefixed SHA-256 token hashes, twelve-hour expiry and a cascading reference to the private subject binding. Session creation requires an existing binding. Lookups read current local tenant/admin attributes; no role is persisted in a cookie or imported from Identity. Removing a binding revokes its sessions. Logout deletes only the supplied Microapps ID session, and the existing sweeper now deletes expired rows from both stores. No tenant-role privileges are granted.

The component regression verifies legacy/ID token rejection across stores, independent logout, current role lookup, unknown subject refusal, expiry/sweep, binding-removal revocation and retained password sessions. Browser cookie selection and exact-origin enforcement are covered by ID-04/05; this storage change does not yet enable ID authentication or alter legacy routes.

Qualification: all 115 fast workspace cases pass (16.20 s build, 20.69 s total; slowest 2.530 s); five focused identity-related cases pass in 9.37 s including an 8.22 s build. Formatting, Clippy and SQLx prepare/check pass with existing test warnings. Owned PostgreSQL 18 only; production and UI are unchanged.


## ID-03: verified allowlisted onboarding

`Sessions::resolve_identity` is reserved for SDK-verified claims. It retains subject-first existing-user linking, then permits new accounts only under the unchanged local address allowlist (the owner address or `@olegpustovit.com`). A single transaction creates a new private tenant, nonadministrator user and subject mapping; it never adopts the nil tenant or grants first-user administration, even on an empty instance. New ID-only users store an invalid PHC marker, not a generated password; ordinary password verification rejects it, including after binary rollback. Existing hashes and roles remain intact. Signup serialization shares the users-table lock with legacy registration; canonical conflict detection rolls back any newly created tenant/user if another binding wins.

The native regression covers empty-instance rejection without writes, eight concurrent first sign-ins with one local account/tenant, exact normalized email, repeat and changed-email resolution, conflicting subjects, independent private tenants, no administrator bootstrap (including the owner address), password rejection, Microapps ID session issuance and injected mapping-insertion failure with exact data rollback followed by successful retry. Six focused identity-related cases pass in 6.07 s including a 5.54 s build; all 116 fast workspace cases pass in 11.42 s including a 7.54 s build (slowest 2.661 s). Formatting, Clippy and SQLx metadata checks pass with existing test warnings. No dependencies, toolchain, HTTP/UI or production state change. Workspace initialization will use the gateway's existing tenant-composition path when SDK callbacks are connected.


## ID-04: gateway browser mode boundaries

Gateway and admin state carry one explicit internal mode. All browser-cookie readers select `__Host-codemode_id_session` plus private Microapps ID storage in Microapps ID mode, including tenant selection, protected API middleware, session metadata and upstream OAuth state binding. Duplicate cookie names fail closed. Legacy and renamed cross-mode tokens cannot authenticate. Microapps ID mode rejects local password login/registration before credential or user writes, suppresses first-user bootstrap metadata and clears only its own Microapps ID session/cookie on exact-origin logout. Agent bearer routing and resource/workspace scopes retain their existing path.

The initial gateway checkpoint kept this mode hardcoded false; ID-05 now derives it from validated default-off SDK composition. UI/provider/deployment qualification is still required before a production switch. The new in-process HTTP test checks mode-specific authentication, public user keys, duplicate/renamed/legacy cookie rejection, password-route closure without user creation, cross-origin logout refusal, own-cookie clearing and working legacy rollback. Existing upstream OAuth/authorization/tenant suites remain green. Full workspace: 117 cases, zero failures, 23.45 s including an 18.66 s build; slowest 2.559 s. Formatting, SQLx metadata freshness and Clippy pass; existing repository test warnings remain. No browser/provider or production cutover is claimed.


## ID-05: shared SDK routes and default-off composition

The gateway consumes the existing `idclient` Rust SDK through the sibling Microapps ID checkout. Rust 1.100.0 is now the pinned toolchain/MSRV, matching the SDK. A reproducible immutable SDK publication/pin remains required before independent deployment; no Identity Git remote was created. The SDK is marked internal/unpublished in Identity commit `a01d50d`. Protocol validation stays inside the shared SDK, including signature/issuer/audience/expiry, verified email, PKCE/state/nonce, flow-cookie protection/consumption and safe local return paths.

`CODEMODE_ID_ENABLED` defaults strictly to false. False ignores unused Microapps ID settings and preserves legacy routes/cookies. True requires a confidential client ID/secret and a nonzero independent 32-byte hex flow key; reusing `CODEMODE_ENCRYPTION_KEY` is refused. The issuer defaults to `https://id.microapps.space`, allows HTTPS origins or exact loopback HTTP for owned tests, and cannot carry credentials, paths, queries or fragments. Callback registration must be exactly `https://CODEMODE_HOSTNAME/auth/callback`. Discovery completes before source import, worker creation, background jobs or listening. Public configuration exposes only `idEnabled`, never client secrets or keys.

Enabled `/auth/login`, `/auth/callback` and POST `/auth/logout` use the SDK's closed router. A single-host boundary rejects unknown/duplicate Host and requires exactly one matching Origin on mutations, supplies no-store/no-referrer headers, and caps the combined auth routes at 60 requests/minute. The resolver accepts verified claims, keeps local roles and invokes transactional subject linking/onboarding. Session creation atomically inserts a new private Microapps ID session and revokes only the prior Microapps ID session from this browser; insertion/deletion failure rolls back both. Logout revokes/clears only this app's Microapps ID session and the SDK flow cookie, leaving global Microapps ID login and legacy/agent sessions untouched.

Native checks use owned PostgreSQL and a loopback discovery/JWKS fixture (no real token callback or production credential). They verify confidential startup guards and secret-safe errors, discovery failure before source/worker initialization, PKCE/nonce/state redirects with exact callback, hostile return-path/host/origin refusal, cookie attributes, verified-claims-only resolution, private nonadmin onboarding, session replacement, injected deletion failure rollback and own-session logout. All 123 fast workspace cases pass: build 4.12 s, total 8.20 s, slowest 2.600 s, unchanged deadlines. Final focused gateway identity cases pass five cases in 5.06 s including a 4.60 s build. Formatting, Clippy and SQLx metadata freshness pass; existing test/shared-fixture and manifest warnings remain. Initial Rust-1.100 cache builds took 139.55 s for core tests and 133.26 s for workspace tests; these are cold-toolchain costs. Warm gateway-module and core-to-gateway rebuilds measure 1.41 s/2.04 s against 5 s/10 s budgets. Existing historical misses elsewhere are not erased.

Dependency qualification passes advisories, licenses, bans and sources through `bash tools/check-dependencies.sh`. The SDK brings `openidconnect` 4.1.0 and RSA 0.9.10; [RUSTSEC-2023-0071](https://rustsec.org/advisories/RUSTSEC-2023-0071.html) concerns private RSA key timing leakage. The SDK only invokes public signature verification (`CoreIdTokenVerifier` → `verify_rsa_signature` → `RsaPublicKey::verify`), never `CoreRsaPrivateSigningKey`, signing or decryption. The same verification-only assessment is documented in Identity's `docs/security-dependencies.md`. This app's wrapper restricts RSA 0.9.10's sole direct dependent to `openidconnect@4.1.0`; any additional dependent fails checks. The advisory exception must be reassessed before private-key use or library changes and removed when upstream adopts patched RSA. No unrelated advisory or license exception is introduced.

UI changes, full actual-provider/browser/tenant/agent qualification, persistent eval smoke/deployment rollback, SDK pin and human production gates remain. Production, existing connections, protected configuration and provider consent are unchanged.
